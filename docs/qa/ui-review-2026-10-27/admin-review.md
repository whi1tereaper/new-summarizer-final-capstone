# Administration and account UI review

Review date: 27 October 2026, Asia/Manila. This is a review of the fresh browser captures in this directory. No application changes are proposed as already implemented, and no commits were made for this review.

The shared palette, readable control contrast, and understated row actions should be retained. The remaining problems are mainly information hierarchy, navigation, filter state, and mobile task access. A consistent token system has not yet produced a consistent page structure.

All displayed accounts, summaries, counts, and research records are synthetic fixtures. Sparse charts, missing word counts, empty audit/registry records, and uncreated storage folders must not be treated as evidence about production activity or service health. The specific range mismatch below is independently confirmed by the page's initial query.

## Prioritized findings

P1 means fix in the next usability pass because the interface can mislead a user or conceal necessary information. P2 means improve in the next layout and content pass.

| Priority | Finding and evidence | Suggested update |
| --- | --- | --- |
| P1 | **The user dashboard displays a false initial date-range state.** The card highlights **30d**, but its chart starts at **1970-01**. This is visible in the [desktop dashboard](screenshots/dashboard-user-light-1440-viewport.png). `dashboard.php` initially requests data from `1970-01-01`, while the shared card marks 30 days selected. | Fetch the same interval that is visibly selected, and show the resolved date range near the chart title. Keep the displayed selection, initial data, and subsequent filter requests synchronized. This is a data-presentation correction before a cosmetic chart redesign. |
| P1 | **Personal Analytics has no corresponding navigation item.** The [personal Analytics screen](screenshots/analytics-user-light-1440-viewport.png) is accessible to a normal account, but its sidebar contains only Summarize, History, and Dashboard. The entry point on the dashboard is the small diagonal-arrow icon in the Analytics card. | Add a clearly labeled Analytics destination for the accounts that can use it, with the current-page state. Replace or supplement the icon-only dashboard entry with **View analytics**. Do not imply that Analytics is administrator-only while exposing a personal report. |
| P1 | **The Analytics page does not visibly communicate the selected preset.** All four date choices look like equally active solid-primary actions in [light desktop](screenshots/analytics-light-1440-viewport.png) and [dark mobile](screenshots/analytics-user-dark-390-viewport.png). The custom date controls are another competing group of primary controls. | Use one range selector with a distinct selected state and matching accessible state; use a secondary treatment for unselected presets. Keep **Apply date range** as the primary action only when a custom interval is being edited. Display the applied range separately from editable values. |
| P1 | **Audit empty-state guidance disappears into the horizontally scrolling table on mobile.** In the [390px full capture](screenshots/audit-logs-light-390-full.png), the result count is visible, but the centered table message is largely offscreen; only a fragment of its explanatory sentence appears at the right. The table retains a 1050px minimum width even with no rows. | Render the empty state outside the horizontal table region at the panel's visible width. Hide the empty table header when appropriate. Keep **No matching events**, the reason, and a Reset filters action visible without horizontal scrolling. |
| P1 | **The administration landing page postpones actual administration.** Its first viewport is dominated by seven Student ID counters, followed by another statistics section. User management, feedback, storage, and landing telemetry sit much farther down. The fresh page is **5,996px tall on desktop and 8,694px on mobile**; see [desktop](screenshots/dashboard-admin-light-1440-full.png) and [mobile](screenshots/dashboard-admin-light-390-full.png). Storage is an anchor within the same document, not a separate view. | Reduce the overview to a compact status summary, exceptions requiring attention, and quick tasks. Put Users, Feedback, and Maintenance into clear task views or local sections with persistent section navigation. Reuse the existing dedicated Student IDs/Analytics screens instead of repeating their large summaries first. |
| P2 | **Student ID Management makes operators read a policy page before doing a task.** On [mobile](screenshots/student-registry-light-390-full.png), the introduction, seven counters, and registry caveats push Add Student IDs well below the first screen. Single-ID entry, bulk import, search, reconciliation, and history all compete in one form-heavy document. Both empty pagination controls remain link-like and active-looking. | Lead with **Add one ID**, **Import a list**, and **Search registry**. Use compact summary counts and progressive help for import/eligibility policy. Separate reconciliation into Advanced maintenance, with its existing safeguards. Disable or omit unavailable Previous/Next controls; show a result count and page position. |
| P2 | **The user dashboard's greeting is too large for a task screen.** The [desktop greeting](screenshots/dashboard-user-light-1440-viewport.png) takes more visual weight than the user's work. A longer fixture name wraps onto a second large line in the [empty-account capture](screenshots/dashboard-empty-light-1440-viewport.png). The primary route to work is labeled **Use my preferred settings**, while no persistent **New summary** action appears in the page header. | Use a compact application page header with a short greeting and **New summary** action. Place recent documents first or beside preferences. Keep preferred settings as a useful secondary shortcut, and reduce analytics to the few measures that help the next task. Format recent timestamps for reading rather than exposing the raw database-style string. |
| P2 | **History is a set of large reading blocks rather than a useful retrieval tool.** The [populated page](screenshots/history-light-1440-viewport.png) has no visible search, type/date filters, or sort control. Summaries and Nutshells repeat the same document title in separate sections. **Access Full Report** is an unexpected name for opening a summary. The [empty state](screenshots/history-empty-light-1440-viewport.png) says **History remains vacant. Initiate a new document analysis** and sends that link to the landing page. | Introduce a compact searchable list with clear Summary/Nutshell type labels, date and sort controls, and **Open summary** actions. Group related outputs for one document where possible. Use **No summaries yet. Create your first summary** with a direct workspace link. Keep the full marketing footer off empty authenticated screens so it does not dominate the only task. |
| P2 | **The evaluation report starts with implementation metadata and misleading navigation.** The [first desktop screen](screenshots/evaluation-report-light-1440-viewport.png) gives considerable space to UUIDs, versions, and long hashes before metric availability. Its Overview/Datasets/Runs tabs appear usable, but their target, `evaluation.php`, currently redirects to the admin dashboard. Its top-level chrome also switches from the app sidebar to the public-style navigation. | Start with dataset, split, run status, completion counts, and measurement availability. Put hashes and detailed provenance in an expanded **Reproducibility details** section. Replace unavailable management tabs with truthful report navigation and a clear **Back to administration** link. Keep Print/CSV/JSON as a coherent contextual toolbar. |
| P2 | **Storage communicates uncertainty as an awkward numeric result.** The [storage panel](screenshots/storage-light-1440-viewport.png) highlights **At least 0 B**, followed by a warning about missing model/cache folders. The distinction between measured zero, uncreated folders, partial measurement, and an actual failure takes several paragraphs to understand. These missing folders belong to the isolated fixture, not a diagnosed production issue. | Make measurement completeness explicit with a **Partial measurement** badge and a short description of the measured scope. Keep known file sizes as values, and show uncreated/unavailable categories separately. Surface last refreshed time next to Refresh, and put technical scope details behind a short help disclosure. |

## Page-by-page assessment

| Page or context | Assessment | Recommended direction |
| --- | --- | --- |
| User dashboard, populated | Clear separation between recent work and preferences, but greeting scale dominates and the first chart's range is wrong. | Correct the range first; then use a compact header, prominent New summary action, and recent-work list. |
| User dashboard, empty | Multiple large empty cards explain the absence of data before helping the user begin. | One concise onboarding state with a direct first-summary action; show preferences and analytics after use. |
| Admin dashboard | One long document combines an overview, management tools, telemetry, feedback, and storage. Mobile requires many screens of scrolling. | Task-based overview and section navigation; remove duplicate summary panels from the first screen. |
| History, populated | Reading is comfortable, but retrieval and scan density do not scale beyond a few items. | Searchable list, type/date controls, shorter previews, consistent Open summary wording. |
| History, empty | The large marketing footer is visually more substantial than the task; the empty-state wording and destination are indirect. | Plain, helpful copy and a direct workspace action; compact authenticated footer. |
| Analytics, admin and personal | Shared color behavior works in both themes. Period selection lacks visual state, and five administrator KPIs create an orphan second row on desktop. | Distinguish selected filters, balance the KPI grid, and prioritize a small set of useful charts. Treat insufficient-data charts explicitly instead of showing an empty-looking plot. |
| Student ID Management | Current controls expose needed operations but make users process too much explanation and too many counters before acting. | Separate entry/import/search workflows; contextual help; consistent pagination. |
| Audit logs | Labels and explicit filtering are understandable on desktop; the filter stack and wide-table empty state are poor mobile defaults. | Compact mobile filter disclosure with active-filter chips and a visible full-width result state. For populated data, emphasize event, actor, and time before raw codes/connection metadata. |
| Storage anchor | The panel's information is legible; its status semantics and location inside the long dashboard weaken wayfinding. | A focused Maintenance view or pane, clear completeness state, concise scope and refreshed time. |
| Evaluation report | The raw report contains useful provenance but is hard to scan and advertises management sections that are not reachable there. | Report-first hierarchy, optional metadata details, accurate navigation, and contextual exports. |
| Sidebar and app navigation | The shared sidebar is visually steady across account/admin screens. Role-based destinations are not fully aligned with accessible pages. | Match navigation to actual available destinations; use a common compact page-header pattern while preserving document-focused result layouts. |

## Suggested implementation sequence

1. Correct the dashboard's initial range/selection mismatch, make Analytics navigation truthful, and repair the mobile audit empty state.
2. Introduce one shared application page-header pattern and a visible selected-filter pattern. Preserve the existing tokens and the horizontal Deactivate/Delete controls.
3. Shorten the admin overview and registry first screen by prioritizing tasks and moving detailed explanation/telemetry into secondary sections.
4. Improve History retrieval and plain-language labels. Reuse a compact authenticated footer rather than adding separate page-specific styling systems.
5. Refine report provenance disclosure and storage completeness language after the core routes and task hierarchy are clear.

This is a proposal only. The review does not change templates, CSS, JavaScript, backend behavior, or production records.
